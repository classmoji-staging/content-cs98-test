Where Does State Live?
 
One question, eight answers
 
* the question for the rest of today: where should this piece of state live? * eight answers, from the least machinery to the most. we'll start with the cheap ones and work down * everything coming up (flux, redux, zustand, server caches, sync) is an answer to this one question
 
where does this state live?
 
* the map for the rest of today: context, flux, redux, zustand, server state are all answers to "where should this piece of state live?" * start at the top. each step down adds machinery: more code, more places for bugs, more for a teammate to learn * 1 derive it: the cheapest state is the state you don't store. a cart total, a filtered list, a count: compute them from what you already have * 2 in the component: useState (or useReducer) inside the one component that needs it * 3 in the parent: two siblings need it, so it moves up to their parent and comes down as props * 4 in the url: anything someone might share, bookmark or refresh into (the shop filters from the routing lecture) * 5 in context: app-wide and rarely changing: theme, language, the signed-in user * 6 in a store: shared and frequently changing; components subscribe to just the slice they read * 7 in a server cache: data that belongs to the server; you hold a copy that can go stale (TanStack Query, SWR, a plain fetch in useEffect, router loaders) * 8 synced everywhere: state that lives on several devices at once (Firebase from Lab 3, sync engines) * the dashed line: above it the data is yours, below it you're borrowing it from the server * we'll go top to bottom; the first four are quick
 
1 · Derive It
 
The state you don't store
 
 
derive it: the state you don't store
 
// ❌ storing what you could compute
const [items, setItems] = useState([])
const [total, setTotal] = useState(0)

useEffect(() => {
  setTotal(items.reduce((t, i) => t + i.price, 0))
}, [items])


// ✅ compute it while you render
const [items, setItems] = useState([])
const total = items.reduce((t, i) => t + i.price, 0)

if you can compute it, don't store it

  • a cart total, a filtered list, an unread count, "is this form valid?"
  • a stored copy has to be kept in sync by hand.
  • unneccesary re-renders

rule of thumb: keep the smallest state you can, compute the rest

* the cheapest state is the state you don't store * your component function runs on every render, so a value computed from items is always in step with items * the useEffect version: React renders with the old total, runs the effect, sets state, renders again. an extra render, and for a moment the screen is wrong * with two pieces of state, every place that changes items also has to remember total. one forgotten setTotal and the cart is lying * this is the first example in React's "You Might Not Need an Effect" (react.dev/learn/you-might-not-need-an-effect) * the cart total shows up again in the sorter at the end; it's the classic trap

useReducer: useState with actions
 
function reducer(state, action) {
  switch (action.type) {
    case 'ADD_TODO':
      return [...state, action.payload]
    case 'REMOVE_TODO':
      return state.filter(t => t.id !== action.payload)
    default:
      return state
  }
}

function TodoApp() {
  const [todos, dispatch] = useReducer(reducer, [])
  return (
    <button onClick={() =>
      dispatch({
        type: 'ADD_TODO',
        payload: { id: Date.now(), text: 'new todo' },
      })
    }>Add</button>
  )
}

for when one component's state gets complicated

  • dispatch an action → the reducer returns the new state
  • all the update logic in one pure function, easy to test
  • still lives in one component (or its parent)

  • more on this
* still in the component: useReducer is useState with the update logic pulled out into one function * reach for it when several pieces of state change together, or one event changes a bunch of things * the reducer is a pure function, (state, action) → new state, so you can test it without React at all * this is the pattern Flux and Redux are built on; we'll see it again in a few minutes * paired with Context it turns into a homemade store, which works fine for small apps (more on that with Context)
 
3 · In the Parent
 
When siblings need it
 
 
in the parent: lift it up
 
function Shop() {
  // both children need the cart, so it lives here
  const [cart, setCart] = useState([])
  const add = (p) => setCart([...cart, p])

  return (
    <>
      <ProductList onAdd={add} />
      <CartBadge count={cart.length} />
    </>
  )
}

// the children just get props
function CartBadge({ count }) {
  return <span className="badge">{count}</span>
}

two siblings need the same data

  • siblings can't talk to each other directly
  • move the state up to their closest shared parent
  • pass the value down, and a callback to change it

rule of thumb: lift it only as high as it needs to go

  • the badge count? cart.length: derived, not stored
* the list adds to the cart, the badge shows it. they're siblings, so the cart moves up to Shop, their closest shared parent, and comes down as props. React's docs call this lifting state up * the children stay simple: CartBadge just renders a number, ProductList just calls onAdd * the badge count isn't its own state: cart.length, derived (section 1 again) * lift only to the closest shared parent. lifting everything to the top of the app "just in case" re-renders more than it needs to and hides who actually uses it
 
when lifting hurts: prop drilling
 
* the picture from the start of class * lift something high enough and it gets handed down through components that never use it, sometimes renamed on the way * that's the signal to move on: context for things that change rarely (next), a store for things that change often
 
4 · In the URL
 
State you can share, bookmark and refresh into
 
 
remember this? useState vs the url
 
* the shop demo from the routing lecture * pick blue + price up, then send the link, in each mode * useState: the filter lives in this tab's memory. refresh or share the link and it's gone * the url: refresh, back, bookmarks and shared links all keep it * next slide: the code for the url version
 
in the url: state you can share
 
import { useSearchParams } from 'react-router'

// /shop?color=blue&sort=price-asc
function Shop() {
  const [params, setParams] = useSearchParams()
  const color = params.get('color') ?? 'all'
  const sort = params.get('sort') ?? 'popular'

  function pickColor(c) {
    setParams((p) => {
      p.set('color', c) // sort stays as it was
      return p
    })
  }
  // ...show the products, filtered and sorted
}


  • refresh: the filter is still there
  • send the link: they see what you see
  • back undoes the last filter

rule of thumb: if someone would share it, bookmark it or refresh into it, put it in the url

  • yes: filters, search, sort, page number, the open tab
  • no: half-typed input, an open dropdown, anything secret
* callback to the "state in the url" demo in the routing deck: same shop, same ?color=blue&sort=price-asc * with useState the filter lives in this tab's memory; refresh or share the link and it's gone. in the url, refresh, back, bookmarks and shared links all keep it * the url IS the state here: read it with params.get(), no separate useState to keep in sync * setParams({ color: c }) replaces the whole query string (sort would vanish); the function form edits the current params and keeps the rest. unlike setState, two calls in the same tick don't stack * everything comes back as a string: Number(params.get('page')) for numbers * keep it small and never put secrets in it: urls end up in history, server logs and screenshots

App-wide, rarely changes
 
 
in context: app-wide, rarely changes
 
const ThemeCtx = createContext('light')

function App() {
  const [theme, setTheme] = useState('light')
  return (
    <ThemeCtx value={theme}>
      <Toolbar />
    </ThemeCtx>

function Button() {
  const theme = useContext(ThemeCtx)
  return <button className={theme}>Hi</button>
}

solves prop drilling!

  • createContext + a provider + useContext
  • any descendant can read the value

limitation:

  • all consumers re-render when value changes
  • no built-in selector to pick a slice
  • fine for theme, auth, locale
  • gets painful for frequently updating data
* React's built-in answer to prop drilling: wrap a subtree in a provider, any descendant can useContext to read it * React 19: you render the context itself as the provider, <ThemeCtx value={theme}>. older code (and most tutorials) write <ThemeCtx.Provider value={theme}>; React 19's release post says .Provider will be deprecated in a future version * great for things that change rarely: theme, locale, auth status * the problem is performance - when the value changes, EVERY consumer re-renders * no way to say "I only care about one field" like useSelector in redux * put a useReducer in a context and you have a homemade store; it works fine for small apps, but it has the same re-render problem * context answers "how does the data get there", not "who changed it, and when". Zustand
 

A small, fast and scalable bearbones state-management solution using simplified flux principles. Has a comfy API based on hooks, isn't boilerplatey or opinionated.

* it is unopinionated, hence we'll have to bring our own opinions!

Why zustand over redux?

  • Simple and un-opinionated
  • Makes hooks the primary means of consuming state
  • Doesn't wrap your app in context providers
  • Can inform components transiently (without causing render)

 

 
main premises
 
* this last one mostly means that it can operate outside of react if you want to, we most likely never will but for very fast paced updates for instance where you might have say a game loop triggering re-renders anyway, but mouse events happening much faster you can update state and not trigger a cascade of re-rendering
 
Step 1: create a store
 
import { create } from 'zustand'

const useBearStore = create((set) => ({
  bears: 0,
  increasePopulation: () => set((state) => ({ bears: state.bears + 1 })),
  removeAllBears: () => set({ bears: 0 }),
}))
 
Step 2: use the store hook to filter state
 
function BearCounter() {
  const bears = useBearStore((state) => state.bears)
  return <h1>{bears} around here ...</h1>
}

function Controls() {
  const increasePopulation = useBearStore((state) => state.increasePopulation)
  return <button onClick={increasePopulation}>one up</button>
}
* the function you pass is a selector: it picks the one slice this component reads * the component re-renders only when that slice changes (compared with Object.is), which is Zustand's big win over one big Context (see the next slide) * picking several values at once? a selector that returns a new object every time would re-render on every change; wrap it: useBearStore(useShallow((s) => ({ bears: s.bears, food: s.food }))) with import { useShallow } from 'zustand/shallow' (Zustand 5) * actions are stable, so a component that only selects increasePopulation never re-renders because of bear counts
 
who re-renders?
 
* guess first: in each mode, which boxes re-render when you add to cart? when you toggle the theme (light/dark mode)? * like a real app, every component you can see reads the theme; only App (which just lays out the page) doesn't * one context: the provider passes value={{ theme, cart, addToCart }}, a new object on every change, so every component that calls useContext(AppContext) re-renders: 9 for either click, even the ones that only care about the theme when you add to cart * zustand + selectors: one store, each component picks a slice; after a change zustand re-runs the selector and compares with Object.is; only changed slices re-render: add to cart = CartBadge + CartPage (2), toggle theme = all 9, same as context * so the theme isn't where selectors help: everything changes color, so everything re-renders either way, and that's fine because it flips once in a while. the cart is the point: it changes all the time and only 2 components show it * even cheaper for dark mode: put a class on and let CSS variables do the colors; then only the toggle re-renders and the browser just repaints * addToCart is an action defined once in the store, so selecting it never causes a re-render * the footnote: App doesn't re-render in either mode because the state lives in a provider or store above it. if App kept the state in useState, everything under it would re-render unless memoized (React Compiler or memo) * the fix within Context is to split it (a ThemeContext and a CartContext); a store with selectors gets you that for free * the table on the right fills in as you try each mode and action

signals: the other way to skip re-renders
 
import { signal, computed } from '@preact/signals-react'
import { useSignals } from '@preact/signals-react/runtime'

// lives outside any component, like a zustand store
const bears = signal(0)
const label = computed(() => `${bears.value} bears`)

function BearCounter() {
  useSignals() // subscribe to whatever this reads
  return <h1>{label.value} around here ...</h1>
}

function Controls() {
  // no selector, no set(): just write it
  return <button onClick={() => bears.value++}>one up</button>
}
  • a signal remembers who read it
  • change it, and only those readers update
  • Solid, Vue, Angular, Svelte 5 and Preact run on them
  • React re-renders instead (the Compiler trims the extras)
  • coming to JavaScript itself? TC39 proposal, Stage 1
* same bear store as the Zustand slides, written with signals * a signal is a box holding a value; reading .value inside a component (or a computed, or an effect) quietly subscribes the reader, and writing .value tells exactly those readers to update * compare: Zustand makes you pick a slice with a selector so the component only re-renders when that slice changes; with signals the subscription comes from just reading the value, so there's no selector to get wrong * computed is derived state that caches itself and only recomputes when a signal it read changes (the "derive it" idea from the start of the lecture) * the other frameworks: Solid (createSignal), Vue (ref), Angular (signal()), Svelte 5 ($state runes), Preact (@preact/signals). They update the DOM directly, with no component re-render at all * React went the other way on purpose: a component is a function you re-run, and the React Compiler auto-memoizes so the re-runs are cheap. React has no built-in signals (as of Oct 2026) * @preact/signals-react: either a Babel plugin, or call useSignals() at the top of a component like above. Works, but it's swimming against React's model, so we're sticking with Zustand * TC39 proposal-signals has been at Stage 1 since 2024; the plan is lots of framework prototyping before it advances: https://github.com/tc39/proposal-signals * Remix 3 doesn't use signals either: component state is a plain variable in a setup closure and you call handle.update() yourself when it changes (handle.signal there is an AbortSignal, not a reactive one) * Jotai's atoms (hidden this term) are the same fine-grained idea inside React: lots of tiny pieces of state that each know their readers

7 · In a Server Cache
 
Server state vs client state
 
 
two kinds of state
 

Client State

  • UI state (modals, tabs, sidebar)
  • form input values
  • user preferences (theme)
  • synchronous, local, ephemeral
  • you own this data

Server State

  • data from your API / database
  • shared across users
  • can become stale
  • asynchronous, remote, persisted
  • you are borrowing this data
* this is a really important distinction that's emerged in the react ecosystem * it's the dashed line on the map from earlier: everything above it you own, below it you're borrowing * zustand/redux are great for client state - UI things that live in the browser * but data from your API is fundamentally different - it lives on the server, can change without you knowing, other users might modify it * treating both the same way leads to bugs: stale data, cache invalidation issues, loading waterfalls
 
the classic useEffect pattern

problems with this approach:

  • no caching - refetches every mount
  • no background refetch
  • race conditions possible
  • duplicate requests across components
  • lots of boilerplate per request
  • data goes stale silently
* this is what we've been doing - useEffect + useState for every API call * it works but you end up reinventing caching, loading states, error handling everywhere * and you miss things: what if the user tabs away and comes back? data might be stale * what if two components need the same data? you fetch it twice * this is where server state libraries come in
 
make impossible states impossible
 
// three separate pieces of state
const [loading, setLoading] = useState(true)
const [error, setError] = useState(null)
const [posts, setPosts] = useState(null)
// loading AND error? error AND posts?
// nothing stops you from setting both

// one piece of state, one status
const [req, setReq] = useState({ status: 'loading' })

// it can only ever be one of:
// { status: 'loading' }
// { status: 'error', error }
// { status: 'success', posts }
  • 3 flags = 8 combinations, only 3 make sense
  • a single status can't contradict itself
  • TanStack Query does exactly this: status is 'pending', 'error' or 'success'
  • TypeScript can enforce it with a union type
  • state machines (XState) take the idea all the way
* look back at the useEffect slide: three useStates for one request * each flag can be true or false (or set or not), so 2 x 2 x 2 = 8 combinations, and the UI has to handle all 8 or quietly break * real bug shape: an error arrives, setError runs, but loading is still true, so the spinner and the error both show * fix the shape of the state instead of adding more if-checks: one object whose status says which case you're in, carrying only the data that case has * TypeScript: type Req = { status: 'loading' } | { status: 'error', error: Error } | { status: 'success', posts: Post[] }, and the compiler won't let you read posts until you've checked status * XState (v5) models a whole UI flow as a state machine: a checkout or a multi-step form; worth a look for complicated flows * the phrase comes from Richard Feldman's elm-conf talk "Making Impossible States Impossible": https://www.youtube.com/watch?v=IcgmSRJHu_8
 
stale-while-revalidate
 
* the idea both TanStack Query and SWR are built on, so it gets its own slide before them * plain useEffect: the component starts from null on every mount, so every visit is a spinner, even if you saw the same list 5 seconds ago * stale-while-revalidate: keep the last answer in a cache (in memory, keyed by the URL / queryKey). on mount: 1) show the cached copy right away, even though it might be out of date (stale), 2) fetch again in the background (revalidate), 3) swap in the fresh data and save it * walk it: posts, home, posts in useEffect mode (spinner both times). switch modes: first visit still spins (empty cache), second is instant. then "+ someone posts", go home and back: old list first, the new post slides in a moment later * the browser only finds out about the new post when it fetches; nothing is pushed from the server (that's the "synced everywhere" place, later) * pull to refresh (drag the list down): useEffect mode resets to null, so the list blinks to a spinner; SWR mode keeps the list on screen while it revalidates. in code that's mutate() from useSWR, or refetch() from useQuery (isFetching is true, data stays) * the trade: for a second the user sees old data. for a feed that's fine; for a bank balance you might show a "refreshing" hint (that's what isValidating / isFetching are for) * the name comes from HTTP caching: Cache-Control: max-age=60, stale-while-revalidate=300 tells a browser or CDN it may serve a stale copy for up to 5 minutes while it refetches in the background (RFC 5861) * SWR also revalidates when you come back to the tab and when the network reconnects; TanStack Query does the same (refetchOnWindowFocus) * TanStack's staleTime (next slide) is how long cached data counts as fresh: inside that window it shows the cache and doesn't refetch at all. default is 0, so it always revalidates like this demo
 
TanStack Query (React Query)
 
import { useQuery } from '@tanstack/react-query'

function Posts() {
  const { data, isPending, error } = useQuery({
    queryKey: ['posts'],
    queryFn: () =>
      fetch('/api/posts').then(r => r.json()),
    staleTime: 5 * 60 * 1000, // 5 min
  })

  if (isPending) return <Spinner />
  if (error) return <Error msg={error} />

  return data.map(p => <Post key={p.id} {...p} />)
}

gives you for free:

  • automatic caching by queryKey
  • background refetching
  • stale-while-revalidate
  • request deduplication
  • retry on failure
  • refetch on window focus
  • loading/error states

tanstack.com/query - also has useMutation for write operations

* TanStack Query is the most popular server state library (v5.104, Oct 2026) * queryKey is like a cache key - same key across components = shared cache * staleTime controls how long before data is considered stale * it returns cached data immediately while refetching in the background * isPending = no data yet (v5 renamed the old isLoading to isPending; the new isLoading means pending AND fetching). there's also a status field: 'pending' | 'error' | 'success', which is exactly the "impossible states" idea * also has useMutation for POST/PUT/DELETE with optimistic updates * wraps your app in a QueryClientProvider similar to how redux had Provider
 
SWR - stale while revalidate
 
import useSWR from 'swr'

const fetcher = (...args) =>
  fetch(...args).then(r => r.json())

function Posts() {
  const { data, error, isLoading } = useSWR(
    '/api/posts',
    fetcher
  )

  if (isLoading) return <Spinner />
  if (error) return <Error msg={error} />

  return data.map(p => <Post key={p.id} {...p} />)
}

SWR by Vercel (Next.js team)

  • simpler API - just key + fetcher
  • same stale-while-revalidate strategy
  • auto refetch on focus/reconnect
  • request deduplication

 

named after the HTTP cache strategy

swr.vercel.app - lighter alternative, great for simpler use cases

* SWR is Vercel's take on the same problem - simpler, smaller * the key IS the URL by convention, fetcher is a separate function * same core idea: return cached data first, revalidate in background * if you're using Next.js this pairs naturally * React Query has more features (mutations, infinite queries, devtools) but SWR is often enough
 
why fetch at the route?
 
* this is the argument for the next slide: why React Router (and Remix before it) wants data loaded at the route, not in components * one page, /sales/invoices/102, three nested routes, each needs its own data: the root needs the user, sales needs the invoice list, the invoice route needs invoice 102 * fetch in components: can't render until its own data is back, so can't even start its fetch. each level waits for the one above: a request waterfall, and a spinner at every level ("render, then fetch") * route loaders: the router matches the URL against the route tree before anything renders, so it already knows all three loaders and starts them together. in framework mode they go out as one request (single fetch) and run in parallel on the server, right next to the database * same server, same work, about 2.1s vs 0.9s in this demo. real apps with 4-5 nested levels and slower phones make the gap bigger * React Router's own docs say it: render-then-fetch "produces network waterfalls and nested spinners" * you can still use TanStack Query with this: prefetch in the loader (queryClient.ensureQueryData) and read with useQuery in the component, so you get both the parallel start and the cache * the fix without a router: hoist the fetches up to the top and pass promises down (or use React's use()), which is basically writing your own loaders

export async function loader() {
  const posts = await db.getPosts()

reactrouter.com

* this is a completely different approach - data fetching happens at the route level, not component level * loader runs on the server before the component renders, so no loading spinner needed * action handles form submissions and mutations, then loaders auto-revalidate * this is the Remix pattern, now React Router framework mode (v8, 8.5.0 in Oct 2026); the routing deck has a framework-mode section we didn't get to in class * the loader code is stripped from the client bundle - safe to use server-only code * we'll see this pattern more when we look at full-stack frameworks
 
optimistic UI: useOptimistic
 
* server state goes both ways: reads (queries, loaders) and writes (mutations) * the server is set to slow (2s); click the heart in each mode, then flip "server fails" * wait mode: spinner, then the count; a failure means the count never moved (try/finally so the spinner always stops) * useOptimistic (React 19): show the expected result right away; when the Action ends, React swaps in the real value, and if the save failed that's the old one, so the UI snaps back * the setter has to run inside an Action (a form action, or startTransition); outside one React warns * the code follows React's docs: wrap the state update after await in startTransition, and catch the error to show a message (an uncaught error in a form action goes to the nearest error boundary) * when to use it: likes, toggles, adding a todo, sending a chat message: small, likely-to-succeed writes where waiting feels broken * TanStack Query's useMutation has the same idea (onMutate + rollback) for code that isn't using form Actions * docs: react.dev/reference/react/useOptimistic

8 · Synced Everywhere
 
State on every device
 
 
synced everywhere: state on every device
 
  • you've done this: Lab 3's notes sync through Firebase, onValue pushes every change to every open tab, on every device
  • sync engines keep a local copy of the data in the browser: reads and writes hit it first, syncing happens in the background
    • Zero (1.0, March 2026), Electric, Jazz
  • CRDTs merge edits made at the same time, even offline (Yjs, from the CRDT demo)

 

the UI feels instant. the hard parts move: conflicts, permissions, what to sync

* last stop on the map, the most machinery and the most powerful: multiplayer, offline, instant * Lab 3: firebase/database's onValue listener re-renders every client when a note changes; that's synced state you already wrote * a sync engine flips the usual model: instead of asking the server and waiting, the app reads and writes a local database and the engine syncs it in the background * Zero (Rocicorp) reached 1.0 in March 2026 (npm @rocicorp/zero 1.0.0, Mar 24 2026); Electric (Postgres sync) and Jazz are other examples. this is often called local-first * CRDTs (Yjs, Automerge) are data structures that merge concurrent edits without a central referee; we saw Yjs merge in the immutability deck and the CRDT demo * the catch: you now have to decide who may see and change what, and what happens when two people edit the same thing * for your projects: Firebase-style listeners are plenty; just know this option exists

none of these change where state lives. they change how much code you write by hand

* React 19 (Dec 5 2024): Actions are async functions passed to a form's action or run in startTransition; useActionState tracks their result and pending state; useOptimistic shows the expected result right away and React reverts it automatically if the action fails (see the like-button interactive) * 19.2 (Oct 1 2025): <Activity mode="hidden"> hides children with display:none, keeps their state, cleans up their effects; switch back and the tab is exactly how you left it * useEffectEvent (19.2): pulls the 'event' part out of an effect so it can read the latest props/state without being a dependency * React Compiler 1.0 (Oct 7 2025): a build-time tool that memoizes components and hooks automatically. React's advice: rely on it for new code, use useMemo/useCallback only when you need precise control; you can pick a compiler template in npm create vite * 19.3 (Sep 9 2026) added <ViewTransition>, which we used in the routing deck * the point: React keeps absorbing patterns people used libraries for; the eight places still decide where the state goes
 
ask your agent: where does this live?
 

💬 “before you add any state, tell me where it should live and why: derived, the component, its parent, the url, context, a store, a server cache, or synced. derive it if you can.”

 

in the diff, watch for:

  • state that could be derived (a stored total, a copied list)
  • a useEffect that copies props into state
  • fetch in useEffect where a query or a loader would do
  • a global store field only one component reads
* you'll write a lot of this with a coding agent; the eight places are a good thing to put in your AGENTS.md or your prompt * asking where it lives forces a reason, and a reason is something you can check * three of the four watch-fors come straight from React's own docs: "You Might Not Need an Effect" (react.dev/learn/you-might-not-need-an-effect) covers derived state, copying props into state, and fetching in effects. the fourth (a store field one component reads) is today's rule of thumb * in code review (yours or the agent's), each of these is a quick win: delete state, delete an effect
